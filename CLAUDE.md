# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local-first AI coding agent as a VS Code extension, built for small local models (7B–14B, primarily `qwen2.5-coder-32k`, i.e. qwen2.5-coder:7b with `num_ctx` 32768) via Ollama or OpenAI-compatible servers. The guiding principle (see `plan.md`, written in Uzbek, which is the original spec): **quality comes from orchestration, not the model.** Code gathers context, constrains output with JSON schemas, validates, and verifies. Prefer fixing agent failures in orchestration over prompt tweaks, and measure with the eval.

## Commands

```bash
npm run build            # esbuild (extension, cli, eval, smoke test) + vite (webview) → dist/
npm run typecheck        # tsc for extension/core + separate tsc for the webview (DOM/JSX config)
npm test                 # vitest unit tests (test/**/*.test.ts only)
npx vitest run test/fuzzyApply.test.ts        # single file
npx vitest run -t "reports parse errors"       # single test by name
npm run test:vscode      # smoke test inside a real VS Code; needs VSCODE_BIN=<electron binary>; SMOKE_E2E=1 adds a chat run with the real model (approval card → Yes → file changed → follow-up)
                         #   Linux: VSCODE_BIN=/snap/code/current/usr/share/code/code (the `code` CLI wrapper detaches and hides output)
                         #   Windows: VSCODE_BIN="$LOCALAPPDATA/Programs/Microsoft VS Code/Code.exe"
node dist/cli.js --root <dir> [-y] [--mode agent|ask|plan] "task"   # headless agent (edits auto-approved, checkpoint first)
node dist/cli.js --root <dir> --chat [-y]   # multi-turn REPL (stdin lines = messages); best way to test conversation behavior
node dist/cli.js --root <dir> [--web duckduckgo|searxng|brave|tavily] [--embed-model nomic-embed-text] "task"   # optional web tools / semantic_search
node dist/cli.js --root <dir> --mcp-server   # Agent Lolo's own tools (repo_map, edit, rename_symbol, ...) over MCP stdio
node dist/cli.js --root <dir> --checkpoints | --restore <id>
node dist/eval.js run [--filter id] [--runs n] [--model m]          # eval → eval/results/<ts>/ (compares with previous run)
node dist/eval.js validate [--filter id]    # every task fails as given; its solution/ passes verify + the hidden check
node dist/eval.js fim [--model qwen2.5-coder:1.5b] [--cpu]          # autocomplete latency p50/p90 (plan's DoD)
node dist/eval.js export --out dataset.jsonl [--exclude id,id] eval/results/<ts>   # passing trajectories → fine-tune samples (hold eval tasks out)
npm run package          # production build + vsce package
```

Requires Ollama at `localhost:11434` with `qwen2.5-coder-32k:latest` for anything that calls the model (cli, eval). Unit tests don't need it. npm 11 blocks install scripts: only esbuild is allowlisted (`allowScripts` in package.json).

## Architecture

**The core never imports `vscode`.** Everything the agent needs from its environment goes through `Host` (`src/host/types.ts`), which has two implementations: `VsCodeHost` (WorkspaceEdit writes, inline review, LSP diagnostics, shell-integration terminal) and `NodeHost` (plain fs, used by the CLI, eval and tests). esbuild bundles `src/cli.ts` and `eval/runner.ts` without `vscode`; keep it that way.

Commands run through `host/shell.ts`: bash (Git Bash on Windows, found next to `git.exe`; never WSL's `bash.exe`), else cmd.exe / `/bin/sh`; `LOLO_SHELL` overrides. `commandEnv()` sets `MSYS_NO_PATHCONV=1` (Git Bash rewrote `"/health"` into a Windows path) and puts `python3`/`pip3` shims first on PATH when `python3` is only the Microsoft Store placeholder. `killTree` uses process groups on POSIX and `taskkill /T` on Windows; Git Bash detaches native children from the Windows process tree, so `ProcessManager.stop` also kills whatever still listens on the port a server reported (`listenerPid`). The VS Code agent terminal is Git Bash on Windows too, and `Host.shell` names the shell in the prompt's Environment line.

Run flow (`src/agent/loop.ts`, `Agent.run`):
1. Checkpoint: a shadow git repo at `.agent/checkpoints` using a separate `GIT_DIR`, so the user's repo is untouched. `restore()` snapshots first and never moves HEAD back.
2. Context. The **system message** holds everything stable: prompt + tool list + `.agent/rules.md` + repo map. The **task message** holds per-run context: @-mentions, active file/selection, diagnostics, git diff stat. The history then only grows at the tail. This ordering is deliberate: it lets Ollama reuse its KV cache between steps. Don't put changing content early in the prompt.
3. Plan (`planner.ts`): schema `{goal, kind, reply, todos}`, in that order (generation order: restating in English before classifying fixes non-English messages). `kind` is chat (answered with `reply`, no tools), question (read-only; ends with the `answer` tool, never `done`) or task. `allowedKinds()` narrows the `kind` enum *without the model*: punctuation-only → chat, a request to remember ("remember that…", "from now on…") → task, question words without request words → question. The plan exchange becomes the history preamble. Checkpoints are taken only once a message is a task.
   `mergeTodos` merges consecutive todos about the same single file ("create src/tax.js", "add computeTax to src/tax.js", "export it") and folds code lines a planner put into the list back into their todo; when the list had code lines the planner is asked once more (they crowded out the real steps). `dropLookOnlyTodos` removes todos that only read/identify/locate (the model redid or undid earlier work in them); check/run todos stay, the user may have asked for them.
   Conversation: the chat (and `cli --chat`) pass earlier turns as text (`ui/transcript.ts: conversationText`) in the task message; `pendingPlanFor()` deterministically turns a short go-ahead ("ha", "ishni boshla", "ok", "давай") after a planned turn into `RunOptions.plan`, which skips the planner. `agent/glossary.ts` appends English hints for Uzbek words.
4. Per todo: one tool call per step. The per-step JSON schema is an `anyOf` with one branch per *enabled* tool, passed as Ollama `format` (outside the prompt, so changing it doesn't break the cache). Then `ToolRegistry.check`: schema, path normalization/sandboxing, then tool-specific `check()`. Errors are phrased for the model to fix.
   Optional tools have a `group` and are offered only when `agent/needs.ts: toolNeeds(todo, message)` (keywords, no model) asks for them; they are announced in a history note, not the system prompt, so the default step stays at ≤ 10 tools: `git` (git_diff/log/blame), `fileops` (move/delete, always confirmed; also offered from the user's message, like `git`, since planners turn "move X" into create + edit; `move_file` rewrites imports of the moved file by code via `tools/importPaths.ts`, since models search for the path as written, not as imported), `refactor` (find_definition, find_references, rename_symbol: LSP through `Host.references`/`renameEdits` in VS Code, tree-sitter `identifierOccurrences` otherwise; one multi-file approval via `Host.proposeWrites`), `process` (start_process/process_logs: a per-run `ProcessManager`, all stopped in `finish()`; a refused server command unlocks it), `web` (web_search/fetch_url, only when the user configured a provider; decided from the user's message too: `@web`, a URL; fetch refuses private addresses on every redirect; long pages go through a separate "extract" model call), `memory` (remember → `.agent/memory.md`, which is in every system prompt), `explore` (a read-only sub-run in ask mode that returns only its answer; large repos, todos naming no file), `symbols` (read_symbol, unlocked once a big file was read). A `ToolDef.available(ctx)` hides tools the run can't use (semantic_search needs `embeddingModel`; web tools need `web`).
   MCP (`src/mcp/`): `McpHub` connects the servers from `.agent/mcp.json`, `.vscode/mcp.json` and settings (stdio or streamable HTTP, kept alive between runs in the extension) and turns their tools into ToolDefs (`group: "mcp"`, schemas reduced to what Ollama `format` and `validate.ts` accept by `schema.ts`). `select.ts` picks ≤ 4 per todo by word overlap, or a whole server for `@mcp:<server>`; the system prompt lists server: tool names so the planner plans with them. Calls need approval unless the tool is `readOnlyHint`. `server.ts` exposes Lolo's own tools the other way.
   If the model calls a hidden optional tool by name, its group is unlocked for the todo (the call is the signal). A todo that only runs one backticked command completes when that command succeeds and more todos follow (`commandTodo`; planners sometimes squeeze a whole task into "Run `dotnet new ...`"), and the step limit grows by 5 (up to 2×) while writes keep applying and nothing failed in the last 3 steps.
   After rename_symbol, later todos about the same rename are completed without the model (planners split renames per file). When the user's message is about failing tests or forbids changing them (`agent/testGuard.ts`), existing test files are read-only for the run (the model otherwise edits the tests until they pass). After 5 reads in a row (agent mode) the observation reminds the model to act. `edit`/`rewrite_file`/`edit_lines` refuse a file the model hasn't seen in this run (`ctx.seen`: read_file/read_symbol, its own writes, @-mentioned files), as Claude Code does; models otherwise guess the lines. Failed test/verify output goes through `tools/testReport.ts` (failure list first). `.agent/rules.md` also supports `after-edit:` (run by the loop after each write) and `before-done:` (joins `verify:`).
5. After a write: diagnostics for the changed files. On `done`: the `verify:` commands from rules, or checks inferred from project files (`context/projectChecks.ts`; detected at that moment, so projects created during the run count). Failures feed back into repair (max 3), except at a todo that isn't the last when the errors name what a later todo changes (`laterTodoFor`): intermediate states of a refactor may not build, so the checks run again after that todo. Deferred checks stay pending (`checksPending`) and run at every later `done` until they pass, even for a todo that changed nothing.
   `run_command` takes `cwd`, times out after 2 min (process group killed / Ctrl+C in the terminal), and hands servers/watchers (`dotnet run` on `Sdk.Web` projects, `npm start/dev`, ...) to `start_process` (background, stopped at run end). It lists files a command created (generators decide the layout the plan guessed); a missing path suggests an existing file with the same name, and `create_file` refuses a second one-per-project file (`Program.cs`, `package.json`, ...) and extension-only names (`.sln`). New packages added by editing a `.csproj`/`package.json` are rejected in favour of `dotnet add package`/`npm install` (`handAddedPackage`). Paths written from the root while `cwd` is set make the command run from the root. Failing dotnet commands/verifies get `nestedProjectProblem` advice when a project sits inside another project's folder. The system prompt carries an Environment line (`context/environment.ts`: OS, shell, date, installed SDK versions) so the model doesn't downgrade frameworks. `node file.js` / `python app.py` / `go run .` count as servers when the file has server code (`.listen(`, `app.run(`, `ListenAndServe`). A failing C# build whose errors are CS0103/CS0246 for well-known framework types gets the `using` directives added by code (`tools/missingImports.ts`, reviewed like any write) and runs again, in `run_command` and in verification. Absolute workspace paths in command output are made relative (`relativizePaths`).
6. Stuck detection: repeating a call made since the last write is blocked (catches A-B-A-B loops), and any write attempt re-allows reads. An identical write already applied in the todo is a repeat too (an "append after ToString" edit was applied 30 times). On 3 repeats or 4 consecutive failures, `onStuck` first runs the project checks: if the todo changed files and they pass, the todo is complete (small models keep "polishing" finished work). Two no-op writes in a row do the same. Otherwise ask the user (interactive hosts) or fail the todo; in question mode the first stuck point instead leaves only the `answer` tool. Ollama generation errors (e.g. "token repeat limit") are retried at a higher temperature. The action schema caps `thought` at `THOUGHT_MAX` (qwen3.5 reasoned in it until the token limit), and `callModel` aborts a thought that passes 1500 characters before any action appears. `ask_user` is not offered to the model at all: 7B models used it instead of working.
7. History compaction (`compaction.ts`) replaces old observations with one-line summaries, but only when over budget, again to keep the prefix stable.

Edit engine (`src/edit/`), where most of the 7B-model reliability lives:
- Format policy (`formats.ts`, `editToolFor`): files ≤ `wholeFileMaxLines` → `rewrite_file` recommended; larger → `edit` (search/replace); after 2 failed edits on a file → `edit_lines` with a numbered view. Hard constraints only: `rewrite_file` is rejected on large files, and `edit_lines` requires line-range mode. `edit` is always allowed (rejecting it measurably hurt the eval). `read_file` shows line numbers only in line-range mode (models copy numbers into `search` otherwise).
- `fuzzyApply`: exact → whitespace-normalized → fuzzy (char-weighted ≥ 0.85, with an ambiguity margin), re-indenting the replacement. It refuses a stale `search` whose `replace` is already present (fuzzy would otherwise match the already-edited line), and an append/prepend edit whose result is already in place. `all: true` replaces every exact occurrence.
- `edit` in `tools/fileTools.ts` resolves what 7B models get wrong around `search`: several matches → the one inside the function the todo or the model's `thought` names (`ctx.todo`, `ctx.thought`), else an error listing each match with its function; `all: true` across functions → only the named one; `replace` that repeats the lines after (or before) the match, e.g. a second closing brace → those lines are replaced (`overlapCandidates`); `replace` that is a complete new version of the definition whose first line `search` matched → the whole old definition is replaced (`redefinition`; otherwise its body stays behind as a dead block that still parses). The repairs apply only when the result parses. `write()` also tries `syntaxRepairs` (C#: `namespace X;` followed by braces → `namespace X { ... }`) before rejecting a write that doesn't parse. Placeholder lines (`// existing implementation`) are refused in `edit` and `create_file`, and so are bodies left out (`isStub`: `{ ... }`, or `// validation logic here` right after the line opening the body; also in `rewrite_file`) unless the todo asks for stubs. `rewrite_file` (and `edit_lines` at 1..0) on a missing path goes through `create_file`: models "rewrite" the new file of a split. `tools/moduleSystem.ts`: ESM syntax written into a CommonJS project (`package.json` without `"type": "module"` and `require`-style files) is converted by code in whole-file writes (`toCommonJs`, plain forms only) and refused otherwise, as is `require` in an ESM one, since models spiral into converting the whole project after Node fails; `write()` refuses a JS file exporting names it doesn't define. `edit/escapes.ts`: JSON has no `\s`/`\d`/`\w`, so under schema decoding a copied regex arrives with a line break (or `\ `) in place of the escape; `write()` and `edit`'s `search` restore broken copies of lines from files the model read (`ctx.seen`). The registry refuses a new code file that the message or todo moves code into until one of the files they name was read (`unreadSources`, policy). Line breaks the model escaped twice (`\\n` in its JSON) are unescaped: in `search`/`replace` only when the unescaped `search` is in the file, in new content when there is no real line break and several `
` before indentation.
- `mergeLazyRewrite` fills `// ... existing code ...` placeholders from the original. `write()` in `tools/fileTools.ts` then preserves EOL, the trailing newline and blank-line spacing, rejects no-op writes, and runs the **syntax guard** (tree-sitter parse errors introduced by the edit; bracket balance for languages without a grammar).
- `diffView.ts`: the inline review writes old (red) + new (green) lines into the real document, with Accept/Reject CodeLens per hunk; the `localAgent.diffPending` context key drives Tab/Esc. Pure logic is in `lineDiff.ts`.

Context (`src/context/`): `treeSitter.ts` loads the grammars from `@vscode/tree-sitter-wasm` (copied to `dist/wasm` by `esbuild.mjs`; resolved from node_modules when running from source). It compiles each query pattern separately so an unsupported pattern is skipped, not fatal, and caches by content hash. `repoMap.ts` is Aider-style: a ref→def file graph, PageRank personalized to focus files (mentions, active file, tabs) and identifiers in the task, and a binary search for the most signatures that fit the budget. `budget.ts` sets the per-section quotas.

Mentions and commands: `@docs:<pkg>` (`context/docs.ts`: installed README from node_modules or site-packages, the npm/PyPI registry only with web enabled), `@mcp:<server>/<resource>`, `@web`. `.agent/commands/*.md` and MCP prompts become `/` commands (`context/slashCommands.ts`), expanded before the run. Pasted images (`RunOptions.images`) go on the task message; `provider.supportsImages()` (Ollama `/api/show` capabilities) refuses them for text-only models. `semantic_search` (`context/semanticIndex.ts`): chunks per top-level definition, embedded via `provider.embed`, cached in `.agent/index` by content hash. `.agent/index/` and `.agent/cache/` are git-ignored and excluded from checkpoints.

Other entry points: `autocomplete/` (FIM: `fim.ts` holds the pure prompt/stop/overlap logic; a whitespace-only cursor line sets the base indent), `inline/` (Ctrl+I), `ui/` (`chatView.ts` extension side; `transcript.ts` event→items reducer and conversation text, shared with the CLI; `protocol.ts` shared types; `webview/` React app built by Vite with its own tsconfig; history in `workspaceState`).

Chat UI (`ui/webview/App.tsx`, `styles.css`) follows Claude Code's panel: framed user messages, assistant rows with dot markers, tool rows "● Read path / ⎿ summary" (click expands output), Claude-style numbered permission options (↑↓ Enter, 1/2/3, Esc), one composer with chips (+ attach, / commands, model, active file, mode; Shift+Tab cycles Ask before edits / Edit automatically / Run everything / Plan / Read-only). Conversations are sessions in workspaceState (history menu). Colors only via `--vscode-*` variables; codicons from `@vscode/codicons` (Vite `base: "./"` keeps the font URL relative). Check visual changes without VS Code: `npm run build && node scripts/webview-preview.mjs`, serve `dist/webview` over http (ES modules don't load from file://), then `google-chrome --headless=new --screenshot=out.png --window-size=440,1100 http://127.0.0.1:<port>/preview-conversation.html` (also `preview-empty`, `preview-command`).

Permissions: during a chat run `VsCodeHost.approvalHandler` turns edits and non-allowlisted commands into approval cards (unified diff from `lineDiff.ts: unifiedDiff`); "always" answers are session state in `ChatViewProvider` (auto-accept edits, allowed command prefixes); "Run everything" (`autoRun`) approves commands too, but the command policy's blocklist still applies before any approval. Without a chat (commands, Ctrl+I) edits go to the inline editor review instead.

Model profiles (`providers/modelProfiles.ts`): agent code reads only the profile (ctx, editFormat, wholeFileMaxLines, FIM tokens, toolMode, `think`, `ollamaOptions`, ...). Built-ins also match without a registry namespace. `qwen3.5` (hybrid SSM/attention, 256k native) runs with `think: false` and `presence_penalty: 0` (its Modelfile's 1.5 distorts copied code); it has no FIM, so `extension.ts` picks an installed model with FIM for autocomplete. Measured on the dev box (RTX 5060 8 GB): qwen3.5:9b 15.8 tok/s at 32k, 13.5 at 64k, 11.2 at 128k; qwen2.5-coder:7b 22 tok/s at 32k. A new model should need only a profile. `toolMode`: `schema` (constrained decoding; the default and by far the most reliable for 7B), `native` (endpoint function calling; qwen2.5-coder via Ollama emits `{"name","arguments"}` as text instead of `tool_calls`, and the parser accepts both), `xml` (tagged text for endpoints without schema support; unconstrained 7B models improvise tags, so the parser also accepts `<tool attr="...">`). History stores each action in the mode's own format (`ToolRegistry.render`), because models copy the format they see. Try modes with `--tool-mode` on the cli/eval.

## Working on the agent

- Every run writes `.agent/trajectories/<ts>.jsonl` (`llm` entries store only the new messages: `from` = index of the first changed message). Read these to diagnose failures before changing prompts or policy.
- Judge changes with `node dist/eval.js run --runs 2` (38 tasks × 2 runs ≈ 20 min on an RTX 4070 Ti; JS/TS, Python, C#, Go, MCP, web, git, conversation). Single runs are noisy. Targets from the plan: tool-call validity ≥ 98%, edit apply ≥ 95% (no-op writes excluded), task pass ≥ 60%. Well-formed calls refused by policy (read before edit, protected tests: `Checked.policy`) are `refusedCalls`, reported apart from invalid calls.
- An eval task is `eval/tasks/<id>/{task.json, repo/, check/, solution/}`. `check/` files are copied in *after* the run (hidden tests). `solution/` is a reference solution (`.remove` lists deleted files); `eval.js validate` checks that the task fails as given and the solution passes the repo's verify commands and the check. The repo's `.agent/rules.md` verify command must succeed on a correct solution; e.g. `python3 -m unittest` exits 5 when no tests exist, so ship a visible test. task.json options: `mcp` (servers; `{task}`/`{workspace}` expand; the mock tracker is `eval/mcp/tracker.cjs`), `web` (recorded answers, `WebConfig.replay`), `approve` (approve commands and calls, like "Run everything"), `before` (earlier messages of the conversation); `setup/` holds uncommitted changes. Checks run in the agent's shell, so they are POSIX on Windows too.
- `test/loop.test.ts` drives `Agent.run` with a scripted model: use it for loop behavior (repeats, guards, planner retries) that needs no real model.
- Test fixtures and planner examples must not mirror eval tasks (an example matching the demo task inflated results once).
- Only `edit` failures (and syntax-guard rejections) count toward the line-range fallback; `recordSuccess` resets the count.
- Syntax-guard feedback shows the would-be lines around the error, and says so when the model's text ends mid-line (an unescaped `"` in the JSON reply cut it short, typical for C# verbatim strings).
- `mergeLazyRewrite` skips filling when the rewrite already contains ≥ 90% of the original lines: a comment like `// Existing tests...` above re-typed code is not a placeholder (filling it duplicated a line and the syntax guard then rejected valid code).
- Fine-tuning: `node dist/eval.js export --exclude <held-out ids>` → `scripts/finetune/train_lora.py` (unsloth QLoRA; ~1 h for 2k samples on a 12 GB GPU) → llama.cpp's `convert_hf_to_gguf.py` + `llama-quantize` (current Ollama imports safetensors only for MLX architectures) → `ollama create lolo-coder -f scripts/finetune/Modelfile`; `lolo-coder` has a built-in profile. The Modelfile must keep qwen2.5-coder's template: one that prints every message sends the system prompt twice (Ollama keeps system messages in `.System` and `.Messages`), which cost the fine-tuned model half its score. Compare on held-out tasks only.
